# NGIS 環境敏感地區查詢 ngis-sensitive

輸入座標或地段地號，輸出落在哪些一級／二級環境敏感地區、重疊面積與比例，
附主管機關與公告文號，可出套疊示意圖。

```
# 地段地號（需 cadastre-check），一行跑完分析＋出圖
python scripts/check.py --parcel 臺南市 龍崎區 番社段 56-4 --map out.png --json out.json

# 多筆地號合併為單一基地（實務上基地常由數筆組成）
python scripts/check.py --parcel 臺南市 西港區 州海段 214 215 216 --map out.png

# 回歸測試（改程式後必跑）
python scripts/selftest.py

# 座標
python scripts/check.py --tm2 190413 2536047
python scripts/check.py --lonlat 121.13 24.03

# 其他
python scripts/check.py --list-layers
python scripts/check.py --parcel 臺南市 龍崎區 番社段 56-4 --map out.png --basemap PHOTO
```

依賴：`shapely`（交集分析）、`Pillow`（出圖）。`--parcel` 另需 cadastre-check skill。

## 最上位原則

**這是「初步評估」，不是正式套繪。** 圖台自己就聲明「所有資料僅供參考用途，不得作為任何形式證明或主張」。正式的應查免查認定必須走環境敏感地區單一窗口查詢平台（eland）或各主管機關。本 skill 的用途是**在送件前先摸清楚有哪些項目要處理**，不能拿來當結論。

**★本機圖資 vs NGIS 不一致的處理（使用者定案 2026-08-10）**：①兩邊都命中、但**分類／屬性不同**（一級 vs 二級、面積、供水別、管理機關…）→ **預設以 NGIS 為主**；②NGIS **0 命中卻本機／前例有**（涵蓋落差）→ 以「有」為準並交叉核對；③**不論哪種不一致，一律先列成清單交使用者逐一確認，確認後才做簡報**——**不得自行拍板、不得過度推論**；④資料來源標明「圖資查得」或「推論」，欄位空白／靠命名反推者不可寫成事實（潮州水庫案：把「供工業用水／南區水資源局」從資料夾名與常識反推寫死，實為誤推——TYPE 欄是供家用、UNIT 欄空白）。

## 踩過的坑（改程式前先看這段）

> 本節是連線與 API 層面的坑。幾何計算與效能的坑另見後面各節：
> 「面積必須在 TM2 算」「環方向」「POST」「上游亂碼」「邊界框篩環」「圖例色票」。

**絕對不要用瀏覽器開這個圖台。** 它同時載入 7 個 WMTS 圖層即時渲染，實測會把 Electron 的 GPU 子程序打死，整個桌面程式當掉（`capturePreviewScreenshot failed` → `GPU process gone`）。本 skill 全程走純文字 HTTP，就是為了繞開這件事。**取 token 也只抓 HTML 原始碼，不要渲染。**

**token 有兩個，第一個是被 `//` 註解掉的失效舊值，而且和生效的那個在同一行。** 用行首錨定的正規表示式會抓錯。必須檢查 match 前方 4 字元內有沒有 `//`：

```python
live = [m.group(1) for m in re.finditer(r'var\s+layerToken\s*=\s*"([A-Za-z0-9_\-]{40,90})"', html)
        if '//' not in html[max(0, m.start()-4):m.start()]]
```

拿錯的症狀是一路 `Invalid Token`，很容易誤判成「token 過期」而往錯方向查。

**token 每次執行重抓，不要寫死或長期快取。** 每次載入頁面都發新的。伺服器 `/rest/info` 宣告 `shortLivedTokenValidity: 60`（分鐘），實測 1 小時後舊 token 仍可用，但**真正的到期時間沒有精確測出**。長時間批次作業要考慮中途換發。

**每個請求都必須帶 `Referer: https://nsp.nlma.gov.tw/ngis/`。** 不帶會被擋。

**只能用 `identify`，不能用 `query`。** 圖層 metadata 的 `capabilities` 寫著 `Query,Map`，但實際呼叫 `/query` 一律回 `Requested operation is not supported by this service`。一級、二級、TCDPDA 全部一樣。**`capabilities` 欄位在這台伺服器上是不可信的。**

**`query` 失敗時會回錯誤物件而不是空結果。** 用 `r.get('features', [])` 取值會把錯誤當成「查無」——這個坑實際造成過誤判。每次都要先檢查 `'error' in response`。

**圖層名稱有尾端空白。** 例如 `"2-05淹水潛勢 "`、`"2-09二級海岸保護區 "`。用名稱比對前務必 `.strip()`。

**`2-22-3地下礦坑分布地區` 是 Polyline，不是 Polygon。** 其餘 53 個圖層都是 Polygon。做幾何運算時要處理這個例外。

**點查詢會漏判部分重疊。** 宗地只有一角落在敏感區內時，形心點查詢會回無命中。要正確判定請用 `ngis.query_polygon()` 傳入宗地環，而不是只查一個點。

## 面積必須在 TM2 算（最容易錯的一步）

identify 回傳的幾何是 **WebMercator(3857)**，該投影在緯度 φ 的面積失真為 1/cos²φ。
台灣約 23°N 就是 **1.18 倍**——直接拿回傳座標算面積會多 18.84%。

實測（臺南市山坡地整片）：

| 算法 | 面積 | 對官方 `Shape.STArea()` 誤差 |
|---|---|---|
| 直接用 WebMercator | 974,616,675 m² | **+18.84%** |
| 先轉 TWD97 TM2 | 820,122,655 m² | **-0.00%** |

`overlay.py` 已內建這個轉換。自行處理幾何時務必先 `geo.merc_to_lonlat` → `geo.lonlat_to_tm2`。

## 環方向：兩種來源要分開處理

**敏感區幾何（ESRI 服務）** 遵守 ESRI 慣例：外環順時針、孔洞逆時針，用帶號面積判別。

**基地環（外部來源）方向不可預期。** QGIS、DXF、手繪、其他 API 給的環可能是任一方向。
把 ESRI 慣例套上去，逆時針的單一外環會被誤判成孔洞、幾何整個歸零——**這個 bug 實際發生過**。
`overlay.py` 因此分成兩個函式：

- `_esri_rings_to_polygon()` — 用帶號面積判別（ESRI 資料專用）
- `_site_rings_to_polygon()` — **與方位無關**，面積最大者為外環，被包含者為孔洞

## 精度：向量 vs PNG

**identify 回傳的向量沒有任何簡化。** 實測同一筆山坡地，顯示參數從 0.15 m/像素到 50 m/像素
共五種組合，頂點數恆為 32 環 / 36,154 頂點；加 `maxAllowableOffset=0` 也一樣。
回來的就是原始權威幾何。

因此：**要算面積、判斷重疊比例 → 用向量**（`overlay.analyze`）。
**只是要張示意圖 → 用 PNG export**（快、輕，且 export 走 Map 能力，是唯一沒被封鎖的能力）。
`mapdraw.py` 採混合：底圖與敏感圖層用圖磚/PNG，**基地範圍用向量描邊**，所以圖上紅框精確。

## 帶幾何的請求一律用 POST（否則大宗地回 404）

大宗地的環會把 URL 撐爆。實測旗山區北勢段291-100（**168 頂點**）用 GET 送 identify：

```
urllib.error.HTTPError: HTTP Error 404: Not Found
```

**回 404 而不是 414，看起來像「服務不存在」，極易往錯方向查。** 實際是查詢字串過長。
`ngis._http(url, data=...)` 會改走 POST，`_identify` 已一律使用。

小宗地（前三組基準都只有 4~22 頂點）不會踩到，**要有大宗地才會暴露**。

## 部分圖層的屬性值在上游就是亂碼

**這不是解碼問題，是 NGIS 資料庫本身壞的。** 實測 2-03嚴重地層下陷地區：

```
COUNTYNAME 的原始 bytes = b'\xc5\xb8q\xdb\xb6m'
UTF-8 / Big5 / CP950 / GBK 全部解不出有意義的中文
```

同一個回應裡欄位「名稱」的中文（`SDE_...嚴重地層下陷地區10407.AREA`）完全正常，
同一欄位在 2-06山坡地 也正常顯示「臺南市」——所以是特定圖層的值壞掉。
2-05淹水潛勢的 `city='0O3n~0'` 亦同。

`ngis._looks_mojibake()` 會濾掉含高位字元的亂碼值。**但純 ASCII 的壞值抓不到**
（`'0O3n~0'` 與合法的 `'24h500r'` 在字元組成上無從區分，硬猜會誤刪正常值）。

**結論：描述性欄位（縣市／鄉鎮／名稱）一律不可盡信，不要直接寫進報告。**
判定本身不受影響——重疊面積、比例、圖層名稱、公告文號都是正確的。

## 效能：一定要先用邊界框篩環（否則會卡死）

敏感區圖層的單一 feature 可能有**兩萬多個環**——實測西港區的 2-05淹水潛勢
單筆就是 **21,787 環 / 189,605 頂點**（山坡地則是 32 環 / 36,154 頂點，差三個數量級）。

不先篩掉遠離基地的環，孔洞歸屬會變成 `21,435 外環 × 352 孔洞 ≈ 750 萬次`
幾何判斷，直接卡死超過兩分鐘。加上邊界框預篩後同一個案子 **6.1 秒**完成。

`_esri_rings_to_polygon(rings, clip_bbox=...)` 的 `clip_bbox` 是效能命脈，不是可選優化。

另一個相關原則：**先在 WebMercator 做交集，只把交集結果轉 TM2 算面積**。
若先把十幾萬頂點整片轉座標再交集，會在純 Python 迴圈裡跑數十萬次投影換算。
（交集在哪個投影做，形狀都對；只有面積會失真，所以面積一定要在 TM2 算。）

## 圖例色票一律取自伺服器

**不可自行配色。** 圖面是伺服器 `export` 用它自己的符號渲染的，圖例若自己配色就會與
圖面不符，報告會誤導。正確做法是打 `/legend?f=json`，回傳每個圖層的 20×20 PNG 色票
（base64），直接貼進圖例。

這樣連填充樣式都會對——山坡地是**綠色斜線**、山崩與地滑是**橄欖綠實心**，
自己配色畫成純色塊就看不出差別。`mapdraw.legend_swatches()` 已封裝並快取。

## 模組

- `scripts/geo.py` — TWD97 TM2 ↔ WGS84 ↔ WebMercator，來回誤差 < 0.1 mm
- `scripts/ngis.py` — token 取得、identify 查詢、結果整理
- `scripts/overlay.py` — 基地 × 敏感區交集分析（需 shapely），輸出重疊面積與比例
- `scripts/mapdraw.py` — 套疊示意圖（需 Pillow），底圖 WMTS、敏感層 export、
  基地向量描邊、圖例取伺服器色票、比例尺、指北針

## 對伺服器的請求量（已實測，目前刻意維持現狀）

單筆地號完整流程（分析＋出圖）**共 7 次請求**：

```
1 次  載入圖台首頁 HTML（取 token）
2 次  identify（一級、二級各一次）
2 次  legend + export
2 次  WMTS 底圖圖磚
```

對照：真人用瀏覽器開一次這個圖台，光初始載入就有**七十幾個請求**（7 個圖層的
圖磚加 JS/設定檔），之後每次平移縮放又是數十個。**跑 10 筆地號還不如一個使用者開一次圖台。**

`robots.txt` 只 `Disallow: /tcdgm`，我們用的路徑不在禁止範圍；伺服器回應無任何
`X-RateLimit-*` 或 `Retry-After` 標頭。

**已知但刻意未做的三件事**（使用者決定維持現狀，不是疏漏）：

1. User-Agent 送的是 `Mozilla/5.0`，並非誠實標示工具身分
2. `fetch_token()` 每次呼叫都載入首頁——批次跑 N 筆就載入 N 次，
   token 有效期至少 1 小時，同批作業其實可重用
3. 無任何請求間隔控制

單筆或少量查詢無虞；**若日後要批次跑數百筆，這三點應該先補**。
